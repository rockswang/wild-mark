# Go-Gui Markdown 查看器：项目开发规划

建议采用“先验证底层风险，再搭建可运行原型，最后完善功能”的三阶段路线。尤其要把 即时模式 GUI 的空闲 CPU、超大文件处理、磁盘发布体积列为原型期的硬性验收项，而不是等功能开发完才测。

Go-Gui 当前公开资料宣称支持 GPU 加速、虚拟化列表、Markdown 视图和无障碍等功能；`go-edit` 则有独立的编辑器缓冲区、逐行高亮缓存和绘制缓存设计。它们提供了不错的起点，但这些特性不等于已经证明你的实际工作负载足够轻。

## 1. 项目目标与技术边界

技术目标

- Go-Gui 原生 GUI，不使用 WebView、浏览器运行时或 HTML/CSS UI。
- `go-edit` 作为编辑器候选，支持 Markdown 语法高亮、行号和基本编辑操作。
- 原生 Markdown 预览，左右分栏，支持滚动、链接、代码块和表格。
- 文件树、快速打开、目录内全文搜索。
- 重点优化长文档和大目录，不追求所见即所得。

  主要风险
- Go-Gui 的即时模式重绘是否导致空闲 CPU 持续占用。
- `go-edit` 当前公开说明中的 32 MiB 文件大小限制。
- Markdown 预览组件对大文档、复杂表格及代码块的性能。
- GPU 后端、字体缓存、CGO 依赖对发布体积和运行内存的影响。

这里有一个重要的前置约束：`go-edit` 的公开 README 明确标注了 32 MiB 文件限制，因此超大文件测试不能只测“能否打开”，还要先确认限制来自哪里，以及是否能通过修改或替换缓冲区解除。

## 2. 原型期：先做性能与可行性验证

建议把原型期拆成四个独立验证工程或可切换的实验模式，不要一开始就把全部功能写进正式应用。

### P0：GUI 空闲资源与渲染验证

目标是确定 Go-Gui 的事件循环、重绘策略和 GPU 后端是否符合轻量化要求。

| 测试场景        | 测量指标               | 目的        |
| ----------- | ------------------ | --------- |
| 窗口刚启动，空白界面  | 启动时间、内存、CPU        | 建立框架基线    |
| 窗口静止 60 秒   | 平均 CPU、峰值 CPU、唤醒频率 | 检查空闲轮询    |
| 窗口最小化 60 秒  | CPU、GPU、内存         | 检查后台重绘    |
| 连续拖动窗口、改变大小 | CPU、帧时间、卡顿         | 检查布局和绘制开销 |
| 快速切换分栏和侧栏   | 帧时间、分配次数           | 检查布局重算    |
| 长时间打开应用     | 内存变化、GC 次数         | 检查缓存增长和泄漏 |

特别关注即时模式 GUI 的 CPU。 即时模式不必然意味着每帧都要高成本重绘，但如果后端持续运行渲染循环，即使窗口内容没有变化，也可能有持续 CPU 消耗。Go-Gui 有绘制缓存和帧性能测量能力的相关说明，但必须在实际 Windows 构建上确认空闲时的行为。

建议把“静止窗口”和“最小化窗口”分开测试。前者验证正常空闲，后者验证是否能够暂停或降低后台渲染频率。

### P1：超大文件加载、编辑和渲染验证

不要把“文件加载成功”和“交互性能合格”混为一谈。一个文件可以很快读入内存，但随后可能在语法高亮、布局计算或每次重绘时卡顿。

建议用固定的合成测试集：

| 测试文件              | 主要测试目标            |
| ----------------- | ----------------- |
| 1 MiB 普通 Markdown | 基础打开和编辑体验         |
| 10 MiB 长文档        | 初步长文档性能           |
| 32 MiB Markdown   | 验证 `go-edit` 已知限制 |
| 64 MiB Markdown   | 验证限制能否解除          |
| 128 MiB 纯文本       | 验证编辑器缓冲区和行索引      |
| 128 MiB Markdown  | 验证解析、排版、渲染的组合压力   |

每个文件都应该生成三种内容分布：

- 普通长段落：大量自然语言，包含中英文和长行。
- 结构密集型：大量标题、列表、引用、表格和链接。
- 代码密集型：大量代码围栏、长代码行和不同语言的高亮。

至少记录以下指标：

- 打开文件的耗时，以及打开后首次可交互的耗时。
- 首屏显示耗时，而不是等待整篇 Markdown 全部排版完成。
- 首次滚动、快速拖动滚动条、跳转到文档末尾的耗时。
- 编辑首字符、连续输入、删除大段文本后的响应延迟。
- 预览更新延迟，尤其是修改文档开头时。
- 峰值工作集、Private Bytes、Go 堆大小、GC 暂停时间。
- 滚动过程中 CPU 占用、帧时间和明显掉帧次数。

关键设计原则：首屏优先、可视区域优先、增量更新。

如果 128 MiB 文件需要几十秒才能完成整篇排版，即使最终可以流畅滚动，也不符合快速打开的目标。预览层应尽可能先呈现首屏，再逐步处理后续内容；编辑器则需要按可见行范围绘制，而不是每次修改都重算整篇文档。

### P2：磁盘体积与依赖验证

磁盘占用要分开测量，不能只看 EXE 文件大小。

| 指标       | 测量内容                  |
| -------- | --------------------- |
| 单文件体积    | Release EXE，分别测压缩与未压缩 |
| 发布目录体积   | EXE、DLL、资源、字体、运行时文件总量 |
| 安装包体积    | 最终分发包                 |
| 安装后磁盘占用  | 实际安装目录和必要的缓存          |
| 首次启动后的缓存 | 字体、配置、索引和其他生成文件       |

建议先测试完全依赖系统字体的版本，再测试打包一套完整字体的版本。中文字体通常是影响发布体积的重要因素之一。

另外，Go-Gui 项目的纯 Go 与 CGO 使用情况要以具体后端和依赖为准。`go-edit` 的核心模块标注为纯 Go，但其 `npad` 示例说明包含需要 SDL2、FreeType 的 CGO 后端，不能据此假设整个桌面程序无需原生依赖。

## 3. 建议的正式架构

原型通过后，再把应用划分成独立模块，避免 GUI 框架侵入文件处理、Markdown 解析和搜索逻辑。

应用层

窗口布局、菜单、快捷键、分栏状态、文件标签

编辑器模块

go-edit 适配层、缓冲区、保存、撤销重做、高亮

预览模块

Markdown AST、布局缓存、可视区域渲染、滚动同步

文件管理模块

目录树、快速打开、文件监听、外部变更检测

搜索模块

文件名匹配、全文检索、结果定位、取消任务

基础设施

Go-Gui、文件系统、Markdown 解析器、文本布局、性能采样

建议在 `internal/` 下按模块划分代码，例如：

```
markdown-viewer/
├── cmd/
│   └── app/
├── internal/
│   ├── app/          # 窗口与应用状态
│   ├── editor/       # go-edit 适配层
│   ├── preview/      # Markdown 解析与原生排版
│   ├── workspace/    # 目录树与文件操作
│   ├── search/       # 文件名与全文搜索
│   ├── document/     # 文件读取、保存、编码
│   └── diagnostics/  # 性能采样与测试工具
├── testdata/
│   ├── small/
│   ├── large/
│   └── pathological/
└── scripts/
    └── benchmark/
```

建议将 `go-edit` 封装在 `internal/editor` 后面。这样，即使后续发现 32 MiB 限制无法合理解除，也能替换编辑器缓冲区或编辑控件，而不必重写文件树、搜索和整个应用状态管理。

## 4. 开发阶段和交付物

1. 阶段 A：技术验证（约 3–5 个工作日）
   - 编译 Go-Gui 最小桌面程序。
   - 运行 `go-edit` 的 `npad` 示例，验证中文输入法、复制粘贴和高亮。
   - 实现空白窗口空闲 CPU 测试。
   - 测量 EXE、发布目录和空闲内存。
   - 验证 32 MiB 文件限制及其来源。
   交付：技术验证报告、基线数据、继续或更换方案的决策。
2. 阶段 B：性能原型（约 5–8 个工作日）
   - 左右分栏和目录侧栏。
   - 编辑区与预览区独立滚动。
   - 打开 1–128 MiB 测试文件。
   - 验证 Markdown 首屏、长文档滚动和增量更新。
   - 加入 CPU、内存和耗时采样。
   交付：可重复运行的性能测试程序和初版指标。
3. 阶段 C：功能 MVP（约 5–10 个工作日）
   - 打开、编辑、保存和外部变更提示。
   - Markdown 语法高亮与原生预览。
   - 目录树、快速打开、全文搜索。
   - 快捷键、主题、错误处理和基础配置。
   交付：可以日常使用的 Windows Release 版本。
4. 阶段 D：稳定性与发布（约 3–5 个工作日）
   - 长时间运行、重复开关文档、超大目录测试。
   - 内存增长、CPU 空转和缓存回收测试。
   - 文件保存安全性、异常退出恢复和搜索取消测试。
   - 检查依赖、许可证、安装包及升级流程。
   交付：发布包、回归测试结果和已知限制清单。

以上工期是单人开发的粗略估算，假设主要使用现有组件。若必须自行实现大文件编辑缓冲区和原生 Markdown 排版，阶段 B、C 可能明显延长。

## 5. 性能验收标准

建议先确定一组原型目标值，测试后再根据硬件和实现方式调整，而不是将其误当作 Go-Gui 已经达到的指标。

以下以 Windows 10/11、64 位 Release 构建、SSD、16 GB 内存的普通开发机为参考；测试时固定显示分辨率、DPI、字体、窗口尺寸和电源模式。

| 指标         | 初版目标         | 测试条件                     |
| ---------- | ------------ | ------------------------ |
| 空白窗口空闲 CPU | 平均不高于 1%     | 静止 60 秒，单独记录最小化          |
| 普通文档打开     | 小于 300 ms    | 1 MiB 文件                 |
| 首屏可见       | 小于 500 ms    | 10 MiB 文档                |
| 普通文档滚动     | 以 60 FPS 为目标 | 典型 1 MiB 文档              |
| 超大文档首屏     | 小于 1 秒为目标    | 128 MiB 文件，SSD           |
| 编辑输入响应     | P95 小于 50 ms | 典型文档和 32 MiB 文档分别测量      |
| 内存         | 先建立基线，再设上限   | 分别记录空闲、10 MiB、128 MiB 文档 |
| 发布包        | 不携带浏览器运行时    | 统计完整发布目录                 |

这里的 128 MiB 首屏目标属于挑战性指标，需要采用流式读取、分块解析或延迟解析等策略；如果所选编辑器必须完整加载并扫描文件，这个目标可能无法实现。

内存指标也不宜只规定一个脱离场景的绝对数值。建议在阶段 A 测出空白窗口基线 \\(M_0\\)，再测出不同文档规模下的峰值工作集 \\(M_n\\)，以增量 \\(M_n-M_0\\) 评价文档处理成本，并同时记录 Go 堆内存和进程 Private Bytes。

## 6. 性能测试工具与记录方式

Windows 上建议使用：

- `Get-Process` 或性能计数器：进程 CPU、工作集、Private Bytes。
- Go `runtime/metrics`、`runtime.ReadMemStats`：堆分配、GC 和对象管理开销。
- `pprof`：CPU 与内存热点。
- `go test -benchmem`：编辑器缓冲区、Markdown 解析器和搜索模块的微基准。
- Windows Performance Recorder / Analyzer：分析持续唤醒、线程调度和后台 CPU 消耗。

每轮测试应记录完整环境和结果，不能只保留最好的一次。至少重复 5 次，分别报告中位数和 P95；冷启动和热启动分开测量。

尤其建议单独做一组空闲渲染专项测试：

1. 启动空白窗口，等待初始化完成。
2. 静止 60 秒，记录每秒 CPU 使用率和帧时间。
3. 静止 5 分钟，观察是否持续产生 GC 或内存增长。
4. 最小化 60 秒，再恢复窗口。
5. 打开长文档，静止后重复上述测试。
6. 对比有无光标闪烁、动画和定时器的结果。

这可以区分框架本身的空闲开销、光标闪烁引起的刷新，以及 Markdown 文档的持续布局成本。

最终建议：把阶段 A 和阶段 B 作为正式开发的准入门槛。 如果 Go-Gui 在空闲 CPU、编辑器文件上限或长文档首屏方面不达标，应先解决这些基础问题，再继续实现功能。否则很容易花大量时间完成一个功能齐全、但在最核心的轻量化目标上不合格的产品。
